Usar el sistema en local

Cómo iniciar la aplicación, comprobar la API REST y probar el recorrido local de webhooks en Windows con XAMPP.

Entorno local configurado

La aplicación y las herramientas de prueba se sirven desde este equipo. Las pruebas locales no envían eventos a servicios externos.

Guía para el proyecto Practicas_Desarrollo · 16 de octubre de 2026

1. Antes de empezar

  1. Abre XAMPP y comprueba que el servicio MySQL/MariaDB esté iniciado.
  2. Abre PowerShell y sitúate en la carpeta del proyecto: 
    Set-Location C:\xampp\htdocs\Practicas_Desarrollo
  3. El archivo local .env.local debe estar configurado. Contiene ajustes privados y no se debe compartir ni subir al repositorio.

2. Iniciar y abrir las páginas

En PowerShell, ejecuta el lanzador. Mantén abierta esa ventana mientras uses el entorno:

powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\local_webhooks.ps1 -Mode All

El modo All inicia los servidores locales y comprueba que estén disponibles.

  • Aplicación Sistema FCThttp://127.0.0.1:8002/index.php
  • Prueba de webhookshttp://127.0.0.1:8003/webhook_test.php
  • Receptor local de webhookshttp://127.0.0.1:8001/webhook.php
  • API REST v1 (base)http://127.0.0.1:8002/api/v1/
Importante: usa exactamente 127.0.0.1 en la página de pruebas de webhooks. El receptor acepta solicitudes POST; si se abre directamente en el navegador con GET, puede responder 405, que es normal.

3. Comprobar el entorno y detenerlo

La ventana de PowerShell indica si los servicios arrancaron correctamente. Al terminar, detén solo los servidores gestionados por el lanzador:

powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\local_webhooks.ps1 -Mode Stop

Los registros de diagnóstico se guardan en %TEMP%\fct-local-servers. Si una URL no responde, comprueba primero que la ventana del lanzador siga abierta, que MySQL esté iniciado y que los puertos 8001, 8002 y 8003 no estén siendo usados por otro programa.

4. Pruebas de webhooks

La página de pruebas permite enviar un evento sintético al receptor local y comprobar también el envío saliente. Todo el recorrido permanece en el equipo.

  • Usa referencias ficticias; no introduzcas datos personales.
  • La recepción de prueba se registra en la bandeja local webhook_inbox.
  • La prueba saliente usa webhook_outbox y entrega el evento al receptor local.
  • Estos eventos de prueba no crean ni modifican expedientes, alumnos, empresas, ofertas o convenios.

5. API REST y autenticación

La API REST v1 se encuentra bajo /api/v1/. Las rutas requieren un token Bearer; por ello, consultar un recurso sin token debe responder 401. No significa que el servidor esté averiado.

  1. Entra en la aplicación con una cuenta administradora.
  2. Abre la sección Tokens API, crea un token y guárdalo de forma segura. El token completo se muestra una sola vez.
  3. Envía el token en la cabecera Authorization de cada solicitud. No lo incluyas en la URL, capturas, código versionado ni logs.

La API aplica los permisos del rol de la cuenta. Consulta docs\api-rest.md para las rutas, permisos y ejemplos de solicitudes.

Pruebas manuales en Docker

Con Docker abierto, inicia sesión como Administración y abre http://localhost:8080/index.php?action=pruebas-integracion (también aparece en el menú como Pruebas API y webhooks).

  • En el probador de API elige método y recurso, escribe el JSON y usa un token activo. El campo del token se borra después de cada solicitud.
  • GET solo consulta. POST y PATCH guardan cambios en la base actual y exigen marcar una confirmación; no tienen borrado automático.
  • La recepción de webhook manda un evento firmado al endpoint local y lo archiva en webhook_inbox.
  • El envío saliente añade un evento sintético a webhook_outbox, ejecuta el despachador y lo entrega al receptor del mismo Docker; no contacta el destino externo.

Usa datos ficticios. Las pruebas de webhook no cambian expedientes, pero los eventos quedan guardados. No incluyas datos personales y no confirmes escrituras de API que no quieras conservar.

6. ¿Se ve lo mismo en local que en el servidor?

La versión local está actualizada para probar la aplicación y los cambios presentes en este proyecto. Las páginas locales se sirven desde la carpeta del proyecto y el entorno de desarrollo ya fue comprobado.

El código y los datos son cosas distintas. La base local de XAMPP es independiente de la base del servidor público. Por tanto, las cuentas, ofertas y demás registros no se sincronizan automáticamente. Por ejemplo, si en local aparece “No hay ofertas aprobadas para mostrar”, puede deberse a que la base local no contiene ofertas aprobadas, aunque sí existan en el servidor.

Los cambios hechos en local tampoco se publican automáticamente. Para que el servidor público muestre una versión nueva hay que desplegar allí el código y aplicar sus migraciones de forma controlada. No copies datos reales o personales del servidor a local sin autorización y medidas de protección.
